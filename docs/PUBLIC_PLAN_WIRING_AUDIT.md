## The two rulings needed first

### 1 · There is no canonical Race Pace Durability plan

The method exists as a **name on two athlete blocks**, not as an object.
`docs/FORM_LABS_METHOD_OBJECT.md` records the concept and says plainly it is
built nowhere. So "wire the public page to the canonical plan" has no referent
yet — there are José's 15 weeks and Hope's 15 weeks.

They are close but not identical:

| | |
| --- | --- |
| Days identical | **79** |
| Days differing, or present for only one | **19** |
| Weekly totals | identical W3–W14; differ at **W2 (39 / 36)** and **W15 (39.2 / 36.2)** |
| W1 long run | José 9 mi · Hope 12 mi |
| Weekly easy budget | José 18 mi · Hope 15 mi |
| Race-pace progression | **identical** — 5 → 6 → 7 → 8 → 10 → 12 → 13.1 |
| Race-pace band | identical — 6:30–6:45 |

The argument of the block is the same for both. The *volume* is not.

**Three ways out, and it is your call:**

- **Publish one athlete's block as the instance**, labelled as such. Cheapest,
  honest, and it means the page says "this is what José is running".
- **Build the method object** — the four objects and two columns already
  specced — and derive the public page from the method rather than an athlete.
  Correct long-term, and it is the thing you eventually sell.
- **Publish the intersection**: the 79 shared days plus the shared progression,
  with the differing days shown as a range. Truthful, but it invents a plan
  nobody is running, and I would not.

### 2 · The prototype's numbers are not the plan's numbers

The static page carries illustrative values. Against the real blocks:

| Prototype says | Real | |
| --- | --- | --- |
| `45 MI` starting volume | **35 mi** (W1) | wrong |
| `~60 MI` peak | **58.4 mi** (W12) | right |
| `12 MI` longest continuous at race pace | **12 mi** (W11), race is 13.1 | right |
| `6:30–6:45 /MI` | 6:30–6:45 | right |
| `3 key days · TUE · THU · SAT` | Tue, Thu, Sat | right |
| Progression `2 → 5 → 6 → 8 → 10 → 12` | **5 → 6 → 7 → 8 → 10 → 12 → 13.1** | differs: no 2, there is a 7, and it ends at the race |
| Every matrix cell | illustrative | all differ |

The whole matrix is placeholder. Starting volume and the progression are the two
places where a *headline claim* would become false if the values were left.

## The six questions

### 1 · Best public route

`/plans/race-pace-durability/` — a directory at the repo root, one `_redirects`
line, one `_headers` block. It must **not** inherit the `/coach/*` headers, which
set `X-Robots-Tag: noindex, nofollow` and `X-Frame-Options: DENY`; this page is
meant to be found and shared.

### 2 · Where the authoritative data lives

`training_blocks` → `training_weeks` → `planned_sessions` (now carrying `role`)
→ `planned_session_versions` → `planned_session_components`, plus
`block_pace_bands` for the pace key and `athlete_marks` / `mark_checkpoints` for
the progression ladder.

**The access problem is the real finding.** Every one of those tables has RLS on
with no `anon` policy, so a signed-out visitor can read none of it.

There is an existing precedent for exactly this: `record_publications` carries a
`publications_public_read` policy granting `anon` SELECT where
`published_at is not null and revoked_at is null`. That is FORM's publish
pattern — an explicit act, revocable, with the ledger recording it.

Two routes:

- **(a) A `security definer` RPC** — `public_plan(slug)` returning the projected
  plan, gated on a `published_plans` row the same way publications are. One
  source of truth, edits reach the page immediately, revocable. Mirrors what
  already exists.
- **(b) A build-time JSON** generated by a script, like `dump_plan.sh`. No anon
  database access at all, so nothing new to secure — but the page is as stale as
  the last build.

**(a) is the right one**, because the whole point of the three-surface
architecture is one prescription behind all of them. Worth knowing: the *dynamic
current week* requirement does **not** need live data — it is derived from the
date in the browser — so (b) would satisfy that part on its own.

### 3 · What can be reused

- `private/render.js` — `authoredMiles`, `workMiles`, `dayLabel`, `rangeLabel`,
  `structureOf`. Pure functions over a version; no athlete evidence.
- `private/record.js` — `escapeHtml`.
- The **weekly-total rule** in `labs.js`: an undated budget row is skipped once a
  week has dated easy days. This is not optional. Ignoring it gives W8 = 64 mi
  instead of **46.4**, because the "Easy — 18 mi across the week" row is counted
  on top of the days it was replaced by. I made exactly that mistake while
  auditing.
- `scripts/design-review/frame.html` and `shots.sh` for the capture pass.

### 4 · What must stay unique to the public page

Everything that is a *projection*: the five hero metrics, the progression
ladder, and the TOTAL row. Labs renders a week; the public page renders a block
in one grid, which Labs has never had to do.

Nothing athlete-specific may cross: no splits, RPE, notes, filed evidence,
ownership, standing observations, portraits, names.

### 5 · Can the static HTML be transplanted without DOM changes?

**Yes, nearly.** The matrix is a plain `<table>` with `<colgroup>`, `<thead>` and
`<tbody>` — 15 week columns and 7 day rows plus TOTAL, which is exactly the shape
of the real data. Hero, metrics, methodology and footer are static copy that
becomes derived values in place.

**One unavoidable change**, and it is small: the current week is hard-coded to
the fourth column in three places — `col.current`, `th.cur`, and
`td:nth-child(4)`. For the week to advance by itself, that must become a class
applied to whichever column is current. Same rule, same appearance, addressed by
class rather than by position.

existing migration, any athlete record.
